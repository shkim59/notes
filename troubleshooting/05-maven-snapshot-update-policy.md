# SNAPSHOT 의존성이 조용히 바뀌는 이유 - Maven updatePolicy

## 들어가며

여러 저장소로 나뉜 공통 모듈이 있다. 프레임워크 코어, 공유 플랫폼, API 모듈 같은 식으로 나뉘어 있고, 각 저장소는 Maven 저장소(Nexus)에 **`4.1.0-SNAPSHOT`** 같은 SNAPSHOT 버전으로 배포된다. 우리 쪽 모듈은 이 아티팩트를 받아서 빌드한다.

```
공통 코어 → 공유 플랫폼 → 각 API 모듈 → 최종 배포 앱
   (모두 x.y.z-SNAPSHOT으로 Nexus에 배포, 서로 의존)
```

## 증상

어느 날 아침, **어제와 똑같은 코드**로 테스트를 돌렸는데 동작이 달라져 있었다.

- 내 저장소에는 새 커밋이 없다.
- `mvn install`도 돌린 적이 없다.
- 그런데 의존하는 모듈의 동작이 바뀌어 있다.

"코드를 안 바꿨는데 바뀌었다"는 건 결국 **코드 말고 다른 무언가가 바뀌었다**는 뜻이다. 의심 대상은 로컬 Maven 저장소(`~/.m2/repository`)였다.

## 원인 추적

### 1. `.m2`에 아티팩트가 들어오는 경로는 두 가지뿐

| 경로 | 언제 일어나나 |
|---|---|
| **의존성 resolve 중 자동 캐싱** | 빌드 도구가 의존성을 찾다가 원격(Nexus)에서 받아 올 때. `compile`·`test`·`package`, IDE의 Maven 재동기화 등 **어떤 빌드든** 트리거된다 |
| **명시적 로컬 설치** | `mvn install`(Gradle은 `publishToMavenLocal`)을 **직접 실행**했을 때만 |

나는 `install`을 안 했으니 2번은 아니다. 그렇다면 1번 — **빌드 도구가 원격에서 새 걸 받아 왔다**는 얘기다. 하지만 이미 로컬에 있는 버전을 왜 다시 받았을까?

### 2. SNAPSHOT은 "주기적으로 다시 확인하는" 버전이다

릴리스 버전(`4.1.0`)은 한 번 받으면 다시 확인하지 않는다. 내용이 바뀌지 않는다는 약속이 있기 때문이다.

SNAPSHOT(`4.1.0-SNAPSHOT`)은 반대로 **"개발 중이라 내용이 계속 바뀔 수 있는 버전"** 이다. 그래서 Maven은 SNAPSHOT을 주기적으로 원격과 비교하는데, 그 주기가 `updatePolicy`다.

```xml
<repository>
    <id>maven-public</id>
    <url>https://nexus.example.com/repository/maven-public/</url>
    <!-- snapshots.updatePolicy 를 지정하지 않으면 기본값은 daily -->
</repository>
```

우리 `pom.xml`에는 `updatePolicy`가 없었다. 그러면 **기본값 `daily`** 가 적용된다. 마지막 확인 이후 하루(날짜 경계)가 지나면, **그날 첫 빌드에서** 원격의 `maven-metadata.xml`을 확인하고 타임스탬프가 다르면 **경고 없이** 새 jar로 로컬 캐시를 덮어쓴다.

### 3. 재구성

```
지난주: 모듈 A 빌드 → .m2에 A-SNAPSHOT(버전1) 캐싱
          ↓  (며칠 동안 A를 다시 빌드하지 않음 → daily 주기 만료)
그사이:  다른 개발자 / CI가 A-SNAPSHOT(버전2)를 Nexus에 deploy
          ↓
오늘:   테스트 실행 → 의존성 resolve → daily 만료 → Nexus 재확인
          → 버전2 발견 → 조용히 다운로드해서 덮어씀
          ↓
결과:   내 코드는 그대로인데 A의 동작이 바뀜
```

오늘 받아진 SNAPSHOT이 있는지는 이렇게 확인할 수 있다.

```bash
find ~/.m2/repository/<groupId 경로> -name "*.jar" -newermt "today 00:00" -ls
```

> 참고로 Gradle 모듈은 `mavenLocal()`을 원격보다 먼저 선언하고 있어서, 로컬에 같은 좌표가 있으면 원격을 아예 보지 않았다. 그래서 이 현상은 Maven 쪽에서만 일어났다. 같은 SNAPSHOT이라도 **빌드 도구에 따라 "어느 시점의 버전"을 쓰는지가 달라진다**는 것도 이번에 알게 됐다.

## 해결

### 즉시 조치 — `updatePolicy=never`

백엔드 전 저장소의 `pom.xml`에 SNAPSHOT 자동 갱신을 끄는 설정을 넣었다.

```xml
<repository>
    <id>maven-public</id>
    <url>https://nexus.example.com/repository/maven-public/</url>
    <snapshots>
        <updatePolicy>never</updatePolicy>
    </snapshots>
</repository>
```

이제 한 번 받아 둔 SNAPSHOT은 **빌드 도중에 저절로 바뀌지 않는다.** 새 버전이 필요하면 `mvn -U`로 내가 원할 때 받는다.

### 그런데 이것만으로는 부족하다

`never`는 **이미 로컬에 캐시가 있을 때만** 효과가 있다.

- 새로 합류한 팀원, CI 서버, `.m2`를 지운 환경에서는 캐시가 없으니 원격에서 받아야 한다. 그 순간 Nexus에 있는 **"그때의 아무 버전"** 을 받는다.
- 즉 문제를 없앤 게 아니라, 터지는 시점을 **"매 빌드"에서 "새 환경을 세팅할 때"로 미룬 것**이다.
- 업데이트를 꺼 두면 진짜 버그 수정도 안 들어오는데, 언제 `-U`를 눌러야 하는지 알려 주는 신호가 없다.

근본 원인은 갱신 정책이 아니라 **`4.1.0-SNAPSHOT`이라는 이름이 불변이 아니라는 것**이다. 같은 버전 문자열이 시간에 따라 다른 내용물을 가리키면, 캐싱 전략을 아무리 잘 짜도 재현성은 보장되지 않는다.

특히 "이 버전을 이 날짜에 배포했다"는 재현 가능한 기준이 필요한 환경에서는, SNAPSHOT으로는 무엇을 배포했는지 특정하기 어렵다.

### 근본 조치 — 버전을 고정한다

그래서 공통 모듈을 관리하는 쪽에 두 가지를 제안했다.

1. **SNAPSHOT 대신 릴리스 버전으로 배포**하고, 소비하는 쪽은 필요할 때만 버전 숫자를 올려서 받기
2. 배포할 때마다 **어느 저장소가 어느 버전(커밋)인지 기록**해 두기

결과적으로 특정 릴리스 버전을 기준선으로 고정하고, 이후 공통 모듈의 변경은 자동으로 받지 않기로 정리됐다. 필요한 수정은 이 기준선 위에서 이어 가고, 기준 버전을 올릴 때는 명시적으로 올린다. 이제 의존성이 움직이지 않으니 "코드를 안 바꿨는데 바뀌는" 일은 구조적으로 생기지 않는다.

## 배운 점

- **"코드를 안 바꿨는데 동작이 바뀌었다"면 코드 밖을 본다.** 의존성 캐시, 환경 변수, 원격 설정처럼 코드 밖에서 바뀔 수 있는 것부터 의심하는 게 빠르다.
- **SNAPSHOT은 "움직이는 버전"이다.** 개발 중인 모듈끼리 주고받을 땐 편하지만, 가져다 쓰는 쪽에서 재현성이 필요하다면 릴리스 버전에 물려야 한다.
- **응급 조치와 근본 조치를 구분한다.** `updatePolicy=never`는 당장의 사고를 막아 주지만 새 환경에서는 다시 터진다. 한계를 알고 쓰면서 근본 해결(버전 고정)을 따로 요청해야 한다.
- 같은 문제가 프론트엔드에도 있었다. 공유 npm 패키지를 `"snapshot"` dist-tag로 받고 있어서, lockfile 없이 설치하면 그 시점의 버전을 받는다. 도구가 달라도 **"움직이는 태그에 의존한다"는 구조가 같으면 문제도 같다.**
