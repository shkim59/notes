> 마틴 파울러, 『리팩터링 2판』 학습 노트

## 리팩터링이란

- 소프트웨어의 **겉보기 동작은 그대로 유지한 채**, 코드를 **이해하고 수정하기 쉽도록** 내부 구조를 바꾸는 기법.
- 아무렇게나 코드를 정리하는 게 아니라, 정해진 방식에 따라 정리하는 것만 리팩터링이다.
- **동작을 보존하는 작은 단계들**로 구성되어 코드가 항상 정상 동작하도록 보장한다.
- 성능 최적화와 비슷해 보이지만 목적이 다르다. 리팩터링은 오히려 성능을 떨어뜨릴 수도 있다.

### 왜 하나

- 설계가 좋아진다.
- 소프트웨어를 이해하기 쉬워진다.
- 버그를 쉽게 찾는다.
- 결과적으로 프로그래밍 속도가 빨라진다.

## 언제 하나

- **기능을 쉽게 추가하기 위해** — 새 기능을 넣기 직전에 구조를 정리한다.
- **코드를 이해하기 쉽게 만들기 위해** — 내부 동작을 이해해야 하는 바로 그 시점에 해야 효과가 크다.
- 간단한 건 즉시 고치고, 오래 걸리는 건 메모해 두었다가 나중에 처리한다.
- 오래 걸리는 리팩터링은 한 번에 하지 말고 조금씩 개선한다.
- **자주 할수록 좋다.**

## 고려 사항

- **코드 소유권은 팀에** 두어 팀원 누구나 수정할 수 있게 하는 게 좋다.
- **지속적 통합(CI) / 트렁크 기반 개발**을 권장한다.
  - 하루에 최소 한 번은 메인 브랜치와 통합한다.
  - 브랜치 간 차이가 크게 벌어지지 않아 머지 복잡도가 낮아지고, 리팩터링을 적용하기도 쉽다.
- **테스트를 견고하게** 작성할수록 리팩터링이 안전해진다.

## 아키텍처

- 코딩 전에 아키텍처를 완벽히 확정하기는 어렵다.
- 간결하게 시작해서 **점진적으로 설계**하는 것을 지향한다.
- 예: 항상 같은 값을 넘기는 매개변수는 미리 만들어 두지 않는다 (필요해지면 그때 추가).

## 개발 프로세스

- **익스트림 프로그래밍(XP)**: 지속적 통합, 자가 테스트 코드, 리팩터링처럼 서로 의존하는 기법을 하나로 묶은 프로세스
- 테스트 주도 개발(TDD)
- 애자일 방법론

## 성능

- 리팩터링은 성능을 떨어뜨릴 수 있지만, **성능 튜닝을 하기 쉽게** 만든다.
- 성능은 **직접 측정해 봐야** 안다.
- 감으로 한 최적화는 대부분 효과가 없다 → 먼저 리팩터링으로 코드를 깔끔하게 하고, 측정 후 병목만 튜닝하는 편이 낫다.
