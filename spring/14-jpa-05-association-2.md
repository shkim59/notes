# JPA 5. 다양한 연관관계 매핑

## 연관관계 매핑 시 고려사항

1. **다중성**: 다대일(N:1), 일대다(1:N), 일대일(1:1), 다대다(N:M)
2. **단방향, 양방향**
   - 테이블: 외래 키 하나로 양쪽 조인 가능 → 방향 개념 없음
   - 객체: 참조 필드가 있는 쪽으로만 참조 가능. 한쪽만 참조하면 단방향, 서로 참조하면 양방향(단방향 2개)
3. **연관관계의 주인**: 양방향일 때 외래 키를 관리할 참조를 지정. 반대편은 조회만 가능

## 다대일 (N:1) - `다`가 주인

<!-- ![다대일 단방향](./images/jpa05-1.png) -->

- 가장 많이 사용하는 연관관계
- 단방향: `Member.team`으로 팀을 알 수 있지만, 팀은 회원을 모른다
- 테이블은 `TEAM_ID` 외래 키로 양쪽 조인이 가능하다

<!-- ![다대일 양방향](./images/jpa05-2.png) -->

- 양방향: 외래 키가 있는 쪽이 주인, 양쪽이 서로 참조

## 일대다 (1:N) - `일`이 주인 (권장하지 않음)

<!-- ![일대다 단방향](./images/jpa05-3.png) -->

- `Team`이 외래 키를 관리하지만, 테이블에서는 항상 N쪽(MEMBER)에 외래 키가 있다
- 엔티티가 관리하는 외래 키가 **다른 테이블**에 있어서 연관관계 관리를 위한 **추가 UPDATE SQL**이 실행된다
- `@JoinColumn`을 꼭 써야 한다 (안 쓰면 조인 테이블 방식이 됨)
- 테이블이 많은 실무에서 추적이 어렵다
- → **일대다 단방향보다는 다대일 양방향을 사용**
- 일대다 양방향: 공식적으로 없는 매핑. `@JoinColumn(insertable=false, updatable=false)`로 읽기 전용 필드를 둬서 흉내낼 수 있지만, 그냥 다대일 양방향을 쓰자

## 일대일 (1:1)

- 다대일과 비슷하며, 외래 키에 유니크 제약이 추가된 형태
- 주 테이블, 대상 테이블 중 어디에 외래 키를 둘지 선택 가능

<!-- ![주 테이블 외래 키 단방향](./images/jpa05-4.png) -->

- **주 테이블에 외래 키** (단방향은 다대일 단방향과 유사, 양방향은 외래 키가 있는 곳이 주인)
  - 객체지향 개발자 선호, JPA 매핑 편리
  - 장점: 주 테이블만 조회해도 대상 테이블 데이터 유무를 알 수 있다
  - 단점: 값이 없으면 외래 키에 null 허용
- **대상 테이블에 외래 키**
  - DB 개발자 선호
  - 장점: 일대일에서 일대다로 바꿀 때 테이블 구조 유지
  - 단점: 단방향은 JPA가 지원하지 않음. 프록시 한계로 **지연 로딩으로 설정해도 항상 즉시 로딩**된다

> 프록시를 만들려면 참조에 값이 있는지(null인지) 알아야 한다. 주 테이블에 외래 키가 있으면 주 테이블만 보면 되지만, 대상 테이블에 외래 키가 있으면 결국 대상 테이블을 조회해야 알 수 있어서 지연 로딩의 의미가 없어진다.

## 다대다 (N:M) - 사용하지 않음

<!-- ![다대다](./images/jpa05-5.png) -->

- 관계형 DB는 정규화된 테이블 2개로 다대다를 표현할 수 없어 **연결 테이블**이 필요하다
- 객체는 컬렉션으로 다대다가 가능 → `@ManyToMany` + `@JoinTable`
- **한계**
  - 연결 테이블에 주문 시간, 수량 같은 추가 데이터를 넣을 수 없다
  - 숨겨진 중간 테이블 때문에 예상치 못한 쿼리가 나간다
- **해결**: 연결 테이블을 엔티티로 승격 → `@ManyToMany`를 `@OneToMany` + `@ManyToOne`으로 풀어낸다
