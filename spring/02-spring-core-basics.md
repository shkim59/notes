## 스프링 생태계

| 영역 | 구성 |
|---|---|
| 핵심 | DI 컨테이너, AOP, 이벤트 등 |
| 웹 | MVC, WebFlux |
| 데이터 접근 | 트랜잭션, JDBC, ORM, XML |
| 기술 통합 | 캐시, 이메일, 원격 접근, 스케줄링 |

### 스프링 부트

스프링을 편리하게 사용할 수 있도록 지원한다.

- 단독으로 실행할 수 있는 스프링 애플리케이션을 쉽게 생성
- Tomcat 같은 웹 서버를 내장해서 별도의 웹 서버 설치가 필요 없음
- 손쉬운 빌드 구성을 위한 starter 종속성 제공
- 스프링과 3rd party 라이브러리 자동 구성
- 메트릭, 상태 확인, 외부 구성 같은 프로덕션 준비 기능 제공
- 관례에 의한 간결한 설정

## 스프링의 핵심

**좋은 객체 지향 애플리케이션 개발을 도와주는 프레임워크.**

### 객체 지향 프로그래밍

- 프로그램을 명령어의 목록으로 보는 시각에서 벗어나, 여러 개의 독립된 단위인 **객체들의 모임**으로 파악한다. 객체는 메시지를 주고받고 데이터를 처리한다.
- 프로그램을 유연하고 변경이 용이하게 만들어서 대규모 소프트웨어 개발에 많이 사용된다.

### 다형성 — 역할과 구현의 분리

- 역할 = 인터페이스, 구현 = 인터페이스를 구현한 객체
- 클라이언트는 대상의 역할(인터페이스)만 알면 된다.
  - 구현 대상의 내부 구조를 몰라도 되고, 내부 구조가 바뀌어도 영향을 받지 않는다.
  - 구현 대상 자체를 바꿔도 영향을 받지 않는다.
- 설계 순서: 역할(인터페이스)을 먼저 정하고 → 구현 객체를 만든다.

## SOLID

| 원칙 | 핵심 |
|---|---|
| **SRP** 단일 책임 | 한 클래스는 하나의 책임만. 책임의 크기는 문맥에 따라 다르며, **중요한 기준은 변경** — 변경 시 파급 효과가 적으면 잘 지킨 것 (예: UI 변경, 객체의 생성과 사용 분리) |
| **OCP** 개방-폐쇄 | 확장에는 열려 있고 변경에는 닫혀 있어야 한다. 인터페이스를 구현한 새 클래스로 기능을 추가 |
| **LSP** 리스코프 치환 | 하위 타입으로 바꿔도 프로그램의 정확성이 깨지지 않아야 한다. 컴파일 성공을 넘어 **인터페이스 규약**을 지키는 것 (예: 자동차의 엑셀이 뒤로 가게 구현하면 위반) |
| **ISP** 인터페이스 분리 | 범용 인터페이스 하나보다 클라이언트별 인터페이스 여러 개가 낫다 (자동차 → 운전 / 정비 인터페이스). 인터페이스가 명확해지고 대체 가능성이 높아진다 |
| **DIP** 의존관계 역전 | 추상화에 의존하고 구체화에 의존하지 말 것. 예: `MemberService`는 `MemberRepository` 인터페이스만 알고 `MemoryMemberRepository`, `JdbcMemberRepository`는 몰라야 한다 |

### 다형성만으로는 부족하다

- 객체 지향의 핵심은 다형성이지만, 다형성만으로는 구현 객체를 바꿀 때 클라이언트 코드도 함께 바뀐다.
- 즉 다형성만으로는 **OCP, DIP를 지킬 수 없다.**
- 스프링은 **DI(의존관계 주입)** 와 **DI 컨테이너**로 다형성 + OCP + DIP를 가능하게 한다.
- 순수 자바로 OCP, DIP를 지키며 개발하면 결국 스프링의 DI 컨테이너 같은 것을 만들게 된다.

### 실무 고민

- 이상적으로는 모든 설계에서 역할과 구현을 분리하고 인터페이스를 부여한다.
- 하지만 인터페이스를 남발하면 **추상화 비용**이 생긴다.
- 확장 가능성이 없다면 구체 클래스를 직접 쓰고, 필요해질 때 리팩터링해서 인터페이스를 도입하는 것도 방법이다.

## IoC와 DI

### 제어의 역전 (IoC)

프로그램의 제어 흐름을 직접 제어하지 않고 **외부에서 관리**하는 것.

| | 제어 흐름 | 예 |
|---|---|---|
| 프레임워크 | 프레임워크가 내 코드를 제어하고 대신 실행 | JUnit |
| 라이브러리 | 내 코드가 직접 제어 흐름을 담당 | |

### 의존관계 주입 (DI)

의존관계는 두 가지로 나눠서 봐야 한다.

- **정적인 클래스 의존관계**: import 코드만 보고 판단할 수 있다. 실행하지 않아도 분석 가능.
- **동적인 객체 인스턴스 의존관계**: 실행 시점에 실제 생성된 인스턴스의 참조가 연결된 관계.

런타임에 외부에서 실제 구현 객체를 생성하고 클라이언트에 전달해서 실제 의존관계가 연결되는 것을 **의존관계 주입**이라 한다.

> DI를 사용하면 **정적인 클래스 의존관계를 바꾸지 않고, 동적인 객체 인스턴스 의존관계를 쉽게 바꿀 수 있다.**

### IoC 컨테이너 = DI 컨테이너

객체를 생성·관리하면서 의존관계를 연결해 주는 것. 최근에는 의존관계 주입에 초점을 맞춰 주로 DI 컨테이너라 부른다(어셈블러, 오브젝트 팩토리라고도 함).

## 스프링 컨테이너 첫 만남

- `ApplicationContext`를 스프링 컨테이너라 한다.
- `@Configuration`이 붙은 클래스를 설정 정보로 사용하고, `@Bean`이 붙은 메서드를 모두 호출해서 반환된 객체를 컨테이너에 등록한다. 이것이 **스프링 빈**이다.
- 빈 이름은 기본적으로 `@Bean` 메서드명을 사용한다.
- `applicationContext.getBean()`으로 조회한다.
