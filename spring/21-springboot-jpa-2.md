# 스프링 부트와 JPA 활용 2

> 인프런 김영한 「실전! 스프링 부트와 JPA 활용 2」 정리

## 용어

- **DTO (Data Transfer Object)**: 계층 간 데이터 교환용 객체. 로직 없이 getter/setter만 가진 순수 데이터 객체
- **DAO (Data Access Object)**: DB에 접근하기 위한 객체. DB 접근 로직과 비즈니스 로직을 분리하기 위해 사용
- **VO (Value Object)**: 값 객체. DTO와 비슷하지만 읽기 전용
- **CQS (Command Query Separation)**
  - Command: 상태를 변경하고 값을 반환하지 않는 메서드
  - Query: 값을 반환하고 상태를 변경하지 않는 메서드
  - 분리하면 성능 최적화, 재사용성, 유지보수성, 가독성이 좋아진다

## 지연 로딩과 N+1 문제

- 지연 로딩으로 엔티티를 조회하면 연관 엔티티는 프록시로 초기화된다
- 프록시의 값을 사용할 때 쿼리가 실행된다
- 엔티티를 여러 건 조회하면 연관 엔티티를 사용할 때마다 쿼리가 실행되어 성능이 떨어진다

### fetch join

- 지연 로딩으로 설정된 연관 엔티티를 조인으로 한 번에 불러오는 기능
- 프록시 대신 실제 엔티티를 조회하므로 쿼리가 한 번만 실행 → N+1 해결

## 컬렉션 조회 (1:N)

**문제점**

- 행이 많은 쪽에 맞춰 결과가 나와 중복 데이터가 생김 → `distinct` 필요
- 컬렉션 페치 조인은 하나만 사용할 수 있다
- 컬렉션 페치 조인을 쓰면 페이징이 불가능하다

**해결 방법**

1. X:1 관계는 모두 페치 조인으로 조회
2. 컬렉션은 지연 로딩으로 조회
3. 최적화 설정 적용
   - `hibernate.default_batch_fetch_size`: 글로벌 설정
   - `@BatchSize`: 개별 설정
   - 프록시 객체를 설정한 size만큼 IN 쿼리로 한 번에 조회

## OSIV (Open Session In View)

### OSIV ON (기본값)

- 최초 DB 커넥션 시작 시점부터 API 응답이 끝날 때까지 영속성 컨텍스트와 DB 커넥션을 유지
- 그래서 View Template이나 컨트롤러에서도 지연 로딩이 가능하다
- **장점**: 엔티티와 지연 로딩을 컨트롤러·뷰에서도 적극 활용할 수 있어 코드 중복이 줄고 유지보수가 쉬움
- **단점**: DB 커넥션을 너무 오래 잡고 있어, 실시간 트래픽이 중요한 애플리케이션에서는 커넥션이 모자라 장애로 이어질 수 있다
  - 예: 컨트롤러에서 외부 API를 호출하면 그 대기 시간 동안 커넥션을 반환하지 못함

### OSIV OFF

![OSIV OFF](./images/sbjpa2-1.png)

- 트랜잭션이 끝나면 영속성 컨텍스트를 닫고 DB 커넥션도 반환 → 커넥션 낭비 없음
- 대신 **모든 지연 로딩을 트랜잭션 안에서 처리**해야 하고, View Template에서 지연 로딩이 동작하지 않는다
- 트랜잭션이 끝나기 전에 지연 로딩을 강제로 호출해 두어야 한다

### CQS로 복잡성 관리

- OSIV를 끈 상태에서 Command와 Query를 분리
- 서비스 계층 분리
  - `~Service`: 핵심 비즈니스 로직
  - `~QueryService`: API 요청에 맞춘 조회 (주로 읽기 전용 트랜잭션)
