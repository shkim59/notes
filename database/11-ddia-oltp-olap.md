# 트랜잭션 처리와 분석 (OLTP vs OLAP)

> 『데이터 중심 애플리케이션 설계』 3장 후반 정리

## 트랜잭션 처리

- 트랜잭션: 논리 단위로 묶인 읽기와 쓰기 그룹
- 트랜잭션 처리: 클라이언트가 지연 시간이 낮은 읽기와 쓰기를 할 수 있게 한다는 의미

## OLTP vs OLAP

| | OLTP (Online Transaction Processing) | OLAP (Online Analytic Processing) |
|---|---|---|
| 용도 | 애플리케이션의 운영 DB | BI, 분석가 |
| 패턴 | 인덱스로 적은 수의 레코드를 조회·수정 | 대량의 레코드를 스캔하고 특정 컬럼을 집계 |
| 요구사항 | 낮은 지연 시간, 높은 가용성 | 대량 처리 성능 |

- OLTP에서 "지난 1년간 매출 합계" 같은 무거운 집계 쿼리를 실행하면, 부하 때문에 실제 사용자의 트랜잭션이 느려질 위험이 있다
- 그래서 운영 DB에 영향을 주지 않도록 **데이터 웨어하우스**라는 별도 저장소로 분리한다

## 데이터 웨어하우스와 ETL

- 여러 OLTP 시스템(결제 DB, 재고 DB, 사용자 로그 등)의 데이터를 한곳에 모은 **읽기 전용 최적화 복사본**
- **ETL (Extract-Transform-Load)**: 데이터를 추출하고, 분석하기 좋게 변환해, 웨어하우스에 적재하는 과정
- 분석가는 운영 시스템의 스키마나 성능 이슈를 신경 쓰지 않고 쿼리할 수 있다

## 분석용 데이터 모델: 별 모양 스키마 (Star Schema)

- **사실 테이블 (Fact Table)**
  - 중심에 위치하며, 비즈니스에서 발생한 이벤트를 기록 (상품 구매, 페이지 클릭 등)
  - 보통 엄청나게 많은 행(수십억 개)
  - 주로 수치값(가격, 수량)과 외래 키로 구성
- **차원 테이블 (Dimension Table)**
  - 사실 테이블의 외래 키가 가리키는 상세 정보 (`product_id` → 상품명, 카테고리 / `store_id` → 매장 위치)
  - 사실 테이블보다 행 수가 훨씬 적음
- **눈송이 스키마 (Snowflake Schema)**
  - 차원 테이블을 더 정규화한 형태 (상품 테이블에서 브랜드 테이블을 또 분리)
  - 쿼리가 복잡해지므로 보통은 비정규화된 별 모양 스키마를 선호

## 컬럼 지향 저장소 (Column-Oriented Storage)

- **로우 지향의 문제**
  - MySQL, PostgreSQL 같은 일반 DB는 행 단위로 저장
  - `SELECT SUM(price) FROM sales`를 실행하면 모든 행을 디스크에서 읽어야 하고, 필요 없는 컬럼까지 로딩되어 I/O 낭비가 크다
- **컬럼 지향의 장점**
  - 데이터를 열 단위로 모아서 저장 (`price` 값들만 모아서)
  - 쿼리에 필요한 컬럼만 읽으면 되므로 빠르다
- **압축**
  - 컬럼 단위로 저장하면 중복 값이 많아 압축 효율이 좋다
  - 비트맵 인코딩, 런 렝스 인코딩으로 크기를 줄이고 메모리 대역폭 효율을 높인다
