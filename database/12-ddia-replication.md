# 복제 (Replication)

> 『데이터 중심 애플리케이션 설계』 5장 정리

네트워크로 연결된 여러 장비에 동일한 데이터의 복사본을 유지하는 것

**왜 복제를 하는가?**

1. **고가용성**: 일부 장비가 다운되어도 시스템이 계속 동작
2. **지연 시간 단축**: 사용자와 지리적으로 가까운 곳에 데이터를 배치
3. **확장성**: 읽기 부하를 여러 장비로 분산

## 1. 리더 기반 복제 (Leader-Based Replication)

대부분의 RDBMS(MySQL, PostgreSQL 등)와 일부 NoSQL(MongoDB 등)이 사용하는 표준 방식. 데이터베이스의 복사본을 저장하는 각 노드를 복제 서버(replica)라고 한다.

- **리더 (Leader / Master / Primary)**
  - 모든 **쓰기** 요청을 처리 (읽기도 가능)
  - 로컬 저장소에 기록한 뒤 복제 로그를 팔로워에게 전송
- **팔로워 (Follower / Slave / Secondary)**
  - **읽기** 요청만 처리
  - 리더로부터 로그를 받아 로컬 DB를 갱신

### 동기식 / 비동기식 복제

| 방식 | 동작 | 장점 | 단점 |
|---|---|---|---|
| **동기식** | 팔로워가 쓰기를 받았다고 확인할 때까지 대기 | 데이터가 항상 일치, 리더가 죽어도 유실 없음 | 팔로워 하나만 죽어도 전체 쓰기가 멈춤 |
| **비동기식** | 팔로워 응답을 기다리지 않고 바로 성공 처리 | 빠른 응답, 팔로워가 느려도 계속 쓰기 가능 | 리더가 죽으면 복제 안 된 데이터 유실 가능 |
| **반동기식** | 팔로워 하나만 동기식, 나머지는 비동기식 | 최소 2곳(리더 + 동기 팔로워)에 데이터 보장 | 안전성과 가용성의 절충 |

### 새로운 팔로워 추가

중단 없이 데이터를 복사하는 방법

1. 리더의 DB 스냅샷을 찍는다
2. 스냅샷을 새 팔로워에 복사한다
3. 팔로워는 스냅샷 이후의 변경 로그를 리더에게 요청한다 (LSN 등 활용)
4. 따라잡으면(catch-up) 정식 팔로워가 된다

### 노드 중단 처리

- **팔로워 장애 (따라잡기 복구)**: 다시 살아나면 마지막으로 처리한 로그 위치를 확인하고 그 이후 로그를 리더에게 요청
- **리더 장애 (Failover)**
  1. 리더가 죽었는지 판단 (보통 타임아웃)
  2. 새 리더 선출
  3. 클라이언트가 새 리더를 보도록 재설정
  - 위험 요소
    - 비동기 복제라면 죽은 리더에만 있던 데이터가 유실될 수 있다
    - 죽은 줄 알았던 리더가 돌아오면 리더가 둘이 되는 **스플릿 브레인**이 발생할 수 있다

### 복제 로그 구현 방식

- **구문 기반 (Statement-based)**: `INSERT`, `UPDATE` SQL을 그대로 전송. `NOW()`, `RAND()` 같은 비결정적 함수에서 불일치 위험
- **쓰기 전 로그 배송 (WAL Shipping)**: 디스크의 바이트 단위 변경사항을 전송. 저장소 엔진과 강하게 결합되어 리더/팔로워 간 버전 차이를 허용하지 않음
- **논리적 로그 (Row-based)**: 행 단위로 변경된 값만 기술. 저장소 엔진과 분리되어 버전 호환성이 좋고, 외부 시스템으로 데이터를 보낼 때(CDC) 유용

## 2. 복제 지연 문제 (Replication Lag)

비동기 복제에서는 리더와 팔로워 사이에 일시적인 불일치가 생기는 **최종적 일관성(Eventual Consistency)** 상태가 된다. 지연이 길어지면 다음 문제가 생긴다.

| 문제 | 상황 | 해결책 |
|---|---|---|
| **자신이 쓴 내용 읽기 (Read-Your-Writes)** | 수정 직후 팔로워에서 읽으면 수정 전 내용이 보임 | 사용자가 수정한 내용은 리더에서 읽도록 라우팅 |
| **단조 읽기 (Monotonic Reads)** | 새로고침할 때 최신 글이 보였다가 다시 옛날 글이 보임 (시간 역전) | 사용자별로 항상 같은 복제 서버에서 읽도록 고정 (User ID 해싱 등) |
| **일관된 순서로 읽기 (Consistent Prefix Reads)** | 파티셔닝 환경에서 답변이 질문보다 먼저 보임 | 인과성이 있는 데이터는 같은 파티션에 기록 |

## 3. 다중 리더 복제 (Multi-Leader Replication)

리더가 하나면 리더가 죽거나 네트워크가 끊겼을 때 쓰기를 전혀 못 한다. 그래서 쓰기를 받는 리더를 여러 개 두기도 한다.

**사용 사례**

- **다중 데이터센터**: 데이터센터마다 리더를 둬서 지연 시간을 줄이고 재해에 대비 (대신 충돌 가능성)
- **오프라인 클라이언트**: 인터넷이 끊겨도 로컬(리더 역할)에 쓰고 나중에 동기화 (캘린더 앱 등)
- **협업 편집**: 구글 독스처럼 여러 사람이 동시에 편집

**쓰기 충돌 처리**

- **충돌 회피**: 특정 레코드의 쓰기는 항상 같은 리더로 라우팅. 가장 단순하고 권장되는 방법
- **일관된 상태로 수렴**
  - **LWW (Last Write Wins)**: 타임스탬프가 가장 높은 쓰기만 남기고 나머지는 버림 → 데이터 유실 위험
  - **병합 (Merge)**: 값을 합치거나, 충돌을 보존해 애플리케이션(사용자)이 선택하게 함

## 4. 리더 없는 복제 (Leaderless Replication)

리더 개념을 없애고 클라이언트가 여러 복제 서버에 직접 쓰기를 보낸다. Amazon Dynamo 스타일 DB(Cassandra, Riak, Voldemort)가 여기에 속한다.

### 정족수 (Quorum)

일부가 실패해도 최소 개수 이상 성공하면 성공으로 본다. 읽을 때도 여러 곳에서 읽어 최신 값을 찾는다.

> **w + r > n**
> - n: 복제 서버 수
> - w: 쓰기가 성공해야 하는 최소 노드 수
> - r: 읽기가 성공해야 하는 최소 노드 수

이 조건을 만족하면(예: n=3, w=2, r=2) 읽기 대상에 최신 값을 가진 노드가 최소 하나는 포함된다.

### 누락된 데이터 복구

- **읽기 복구 (Read Repair)**: 읽을 때 여러 노드의 버전을 비교해, 오래된 노드에 최신 값을 다시 써준다
- **안티 엔트로피 (Anti-entropy)**: 백그라운드 프로세스가 복제 서버 간 차이를 찾아 동기화한다

### 동시 쓰기 감지

리더가 없으면 쓰기 순서가 불명확하다.

- **이전 발생 (Happens-before)**: 작업 B가 작업 A를 알고 있거나 의존하면 인과성이 있다. 서로 모르면 **동시 작업**이다
- **해결책**
  - **LWW**: 시간순으로 덮어씀 → 데이터 유실 가능
  - **버전 벡터 (Version Vector)**: 복제본별 버전 번호를 추적해, 덮어써도 되는 값인지 병합해야 하는 동시 쓰기(형제 값, siblings)인지 구분

## 요약

| 방식 | 특징 |
|---|---|
| 단일 리더 | 가장 대중적이고 이해하기 쉽지만, 리더가 병목이 될 수 있다 |
| 다중 리더 | 데이터센터 간 복제나 오프라인 작업에 좋지만, 충돌 해결이 복잡하다 |
| 리더 없음 | 가용성이 매우 높지만, 정족수 설정과 동시성 제어가 어렵다 |
