# 데이터 모델과 질의 언어

> 『데이터 중심 애플리케이션 설계』 2장 정리

## 1. 데이터 모델과 추상화 계층

- 데이터 모델은 **소프트웨어를 어떻게 설계하고 문제를 어떻게 사고하는지**에 직접적인 영향을 준다
- 대부분의 애플리케이션은 **여러 데이터 모델을 계층적으로 쌓아 올린 구조**를 가진다
- 각 계층의 핵심 과제는 **상위 계층의 데이터 모델을 하위 계층 관점에서 어떻게 표현할 것인가**

```text
현실 세계
 └─ 객체 / 데이터 구조 + API
     └─ JSON / XML / RDB 같은 범용 데이터 모델
         └─ 메모리 · 디스크 · 네트워크 상의 바이트
             └─ 전류 · 빛의 파동 · 자기장
```

- 각 계층은 명확한 데이터 모델을 제공하고, 하위 계층의 복잡성을 감춘다 → **추상화**

## 2. 관계형 모델

- 데이터는 **릴레이션(테이블)**으로 구성
- 릴레이션은 **순서 없는 튜플(row)의 집합**
- 관계는 포인터가 아니라 **값(ID)**으로 표현
- 등장 배경: 비즈니스 데이터 처리 (트랜잭션 처리, 일괄 처리)
- 핵심 목표: **선언적 인터페이스(SQL)** 뒤로 저장 방식, 인덱스, 접근 경로 같은 **구현 세부 사항을 숨기는 것**

> 관계형 모델의 본질은 JOIN이 아니라 데이터 접근 경로와의 분리

## 3. NoSQL의 등장 배경

- 대규모 데이터셋이나 매우 높은 쓰기 처리량을 관계형보다 쉽게 달성할 수 있는 확장성
- 동적이고 표현력이 풍부한 데이터 모델

> 💡 **다중 저장소 지속성 (Polyglot Persistence)**: 관계형 DB와 다양한 비관계형 DB가 함께 사용되는 것

## 4. 객체 관계형 불일치 (Impedance Mismatch)

| 객체지향 언어 | 관계형 모델 |
|---|---|
| 중첩 구조, 참조, 컬렉션 | 테이블, 행, 외래키 |

→ 자연스럽게 1:1 매핑되지 않음

- ORM은 전환 계층의 boilerplate를 줄여주지만, JOIN, 지연 로딩, 트랜잭션 경계, N+1 문제 등을 **완전히 숨길 수는 없다**
- JSON 문서는 함께 조회되는 데이터를 한 덩어리로 저장하므로 다중 테이블보다 **지역성(Locality)**이 좋다

## 5. 문서 모델

- **함께 조회되는 데이터는 하나의 문서로 저장**
- 스키마가 유연함
  - **Schema-on-write (관계형)**: 데이터가 들어올 때 형식을 검사. 정적 타입 언어와 비슷
  - **Schema-on-read (문서)**: 데이터는 자유롭게 넣고 읽을 때 애플리케이션이 구조를 해석. 동적 타입 언어와 비슷
  - 컬럼 정의를 미리 정하지 않아도 되고, 같은 컬렉션에 서로 다른 구조의 문서가 공존할 수 있다
- JOIN을 전제로 설계되지 않음 (불가능하진 않음)
  - 관계 결합은 애플리케이션 레벨에서 직접 수행하거나 중복 저장을 허용
- 애플리케이션 데이터가 일대다 관계의 트리이고 보통 한 번에 전체를 적재한다면 문서 모델이 적합하다

## 6. 다대일 / 다대다 관계와 정규화

> 중복 데이터를 정규화하려면 다대일 또는 다대다 관계가 필요

- 문서 모델은 중첩 구조에 강하지만, **참조 대상이 많아질수록** 중복, 갱신 비용, 불일치 위험이 증가
- 관계형 모델은 ID 기반 참조와 JOIN으로 재사용이 쉽고 중복 제거가 쉽다

## 7. 계층 모델과 네트워크 모델

**계층 모델 (Hierarchical Model)**

- 트리 구조. 각 레코드는 **단 하나의 부모만** 가짐 → 문서 모델과 구조적으로 유사
- 한계: 다대다 관계 표현 불가, 구조 변경이 어려움

**네트워크 모델**

- 계층 모델의 일반화. 레코드는 **여러 부모**를 가질 수 있고, 관계를 **포인터**로 표현
- 최상위 레코드에서 시작해 정의된 연결 경로를 따라야만 접근 가능 → **접근 경로(access path)**
- 데이터 구조 = 접근 경로이므로, 경로가 바뀌면 애플리케이션 코드도 바뀌어야 함

## 8. 관계형 모델의 장점

| 구분 | 네트워크 모델 | 관계형 모델 |
|---|---|---|
| 관계 표현 | 포인터 | 값(ID) |
| 접근 방식 | 경로 기반 | 선언적 질의 |
| 구조 변경 | 애플리케이션 수정 필요 | SQL만 변경 |
| 유연성 | 낮음 | 매우 높음 |

## 9. 데이터를 위한 질의 언어

### 명령형 vs 선언형

- **명령형**: 특정 순서로 특정 연산을 수행하게끔 컴퓨터에게 지시
- **선언형** (SQL, 관계 대수): 목표를 달성하는 방법이 아니라 **알고자 하는 데이터의 패턴**을 지정
  - 결과가 충족해야 하는 조건과, 데이터를 어떻게 변환(정렬, 그룹화, 집계)할지만 기술
  - 명령형 API보다 간결하다
  - DB 엔진의 구현이 숨겨져 있어 질의를 바꾸지 않고도 DB 성능을 개선할 수 있다
  - 알고리즘이 아닌 결과의 패턴만 지정하므로 병렬 실행에 유리하다

### 맵리듀스 질의

- 많은 컴퓨터에서 대량의 데이터를 처리하기 위한 프로그래밍 모델
- 많은 문서를 대상으로 읽기 전용 질의를 수행할 때 사용
- 선언형과 명령형의 중간

### 그래프형 데이터 모델

- 다대다 관계가 매우 일반적인 경우에 사용 (내비게이션, 페이지랭크 등)
- **속성 그래프**
  - 정점: 고유 식별자, 유출 간선 집합, 유입 간선 집합, 속성 컬렉션(키-값)
  - 간선: 고유 식별자, 꼬리 정점(시작), 머리 정점(끝), 관계 유형 레이블, 속성 컬렉션
- **사이퍼(Cypher)**: 속성 그래프를 위한 선언형 질의 언어
- SQL에서 그래프 질의는 어렵다 → 애플리케이션에 맞는 데이터 모델을 선택하는 것이 중요
