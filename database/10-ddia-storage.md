# 저장소와 검색

> 『데이터 중심 애플리케이션 설계』 3장 정리

- 저장소 엔진은 **특정 작업부하(workload)**에 최적화되도록 설계된다
  - 쓰기 위주 (append-heavy) / 읽기 위주 (point lookup, range scan)
  - 랜덤 접근 vs 순차 접근
- 성능 튜닝을 하려면 엔진이 내부에서 **어떤 작업을 하는지**, 어떤 연산이 **싸고 비싼지** 이해해야 한다

## 1. 저장소 엔진의 두 가지 접근 방식

### 로그 구조 저장소 (Log-Structured)

- 데이터를 **추가 전용(append-only)**으로 기록하고, 기존 데이터를 덮어쓰지 않는다
- 쓰기 성능이 매우 좋음 (순차 쓰기)
- 읽기는 비효율적일 수 있음 (데이터가 흩어짐)
- 주로 색인과 결합해 사용 (LSM-tree 등)

### 페이지 지향 저장소 (Page-Oriented)

- 디스크를 **고정 크기 페이지(보통 4KB)** 단위로 관리. 특정 페이지를 읽고, 수정하고, 다시 기록
- 읽기 패턴이 예측 가능
- 쓰기 시 랜덤 I/O 발생 가능
- 전통적인 관계형 DB에서 많이 사용

## 2. 로그 (Log)

- **추가 전용 레코드 시퀀스**. 항상 맨 뒤에만 기록해 디스크의 순차 쓰기 성능을 최대한 활용

```text
[record1][record2][record3][record4]...
```

- 로그만으로는 특정 키를 빠르게 찾기 어렵다 → **색인** 필요

## 3. 색인 (Index)

- **특정 키의 값을 빠르게 찾기 위한 데이터 구조**. 원하는 데이터의 위치를 알려주는 이정표 역할의 메타데이터
- 기본 데이터에서 **파생된 추가 구조**
  - 색인을 추가/삭제해도 데이터 자체는 변하지 않고 질의 성능만 변한다
- **트레이드오프**: 읽기 성능은 좋아지지만, 데이터를 쓸 때마다 색인도 갱신해야 해서 쓰기 오버헤드가 생긴다

### 모든 데이터를 자동으로 색인하지 않는 이유

- 색인은 공짜가 아니다 (디스크 공간, 쓰기 성능 저하)
- 그래서 개발자나 DBA가 **필요한 색인만 선택**하도록 설계되어 있다 → 오버헤드를 최소화하면서 읽기 성능을 높임

## 4. 해시 색인 (Hash Index)

- **키 → 값** 구조, 보통 해시맵으로 구현
- 특정 키 조회(point lookup)는 매우 빠름
- 범위 검색(range scan)은 불가능
- 주로 키-값 저장소에서 사용

## 5. 인메모리 데이터 구조

- 프로그램 실행 중 **RAM에 올려 직접 접근**하는 데이터 표현 방식
- 디스크 I/O 없이 CPU가 바로 접근 → 매우 빠름
- 메모리 한계와 영속성 문제가 있어 디스크 구조와 결합이 필요

## 6. B-트리 (페이지 지향 색인의 대표)

- 데이터를 **고정 크기 페이지(보통 4KB)**로 관리하고, 한 번에 하나의 페이지를 읽거나 쓴다
- 각 페이지는 주소로 식별되고, 다른 페이지를 참조할 수 있어 **트리 구조**를 이룬다
- 구성: 루트 페이지 / 내부 페이지(키 + 하위 페이지 참조) / 리프 페이지(키와 값, 또는 값의 위치)

**검색**

1. 루트 페이지에서 시작
2. 키를 비교해 하위 페이지로 이동
3. 반복해서 리프 페이지에 도달 → 값 획득

**갱신**

1. 리프 페이지 검색
2. 페이지 내용 수정
3. 해당 페이지를 디스크에 다시 기록
   - 읽기/쓰기 모두 페이지 단위 I/O 발생
   - 랜덤 쓰기가 성능 병목이 될 수 있음
