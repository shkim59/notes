## EC2

AWS의 클라우드 컴퓨팅 서비스 (IaaS).

### 인스턴스 유형

| 유형 | 적합한 작업 | 접두어 |
|---|---|---|
| 범용 | 웹 서버, 코드 저장소 등 다양한 작업. 컴퓨팅·메모리·네트워크 균형 | t, m |
| 컴퓨팅 최적화 | 배치 처리, 미디어 트랜스코딩, 고성능 웹 서버, HPC, 머신러닝, 전용 게임 서버 | c |
| 메모리 최적화 | 메모리에서 대규모 데이터셋 처리, 고성능 RDB/NoSQL, 분산 캐시(ElastiCache), BI용 인메모리 DB, 대규모 비정형 데이터 실시간 처리 | r, x1, z1 |
| 스토리지 최적화 | 로컬 스토리지의 대규모 데이터셋 접근, 고빈도 OLTP, 인메모리 DB 캐시(Redis), DW, 분산 파일 시스템 | i, d, h1 |

### 인스턴스 시작

- 이름·태그 → OS 이미지(AMI) → 인스턴스 유형 → **키 페어**(SSH 접속용) → 네트워크(보안 그룹) → 스토리지 순으로 설정한다.
- **사용자 데이터(User Data) 스크립트**로 부트스트래핑할 수 있다. 인스턴스가 **처음 시작될 때 한 번만** 루트 권한으로 실행되며, 업데이트·소프트웨어 설치 등에 쓴다.
- 인스턴스를 중지했다 다시 시작하면 **퍼블릭 IP가 바뀔 수 있다.**

### 보안 그룹

- 인스턴스 앞의 **방화벽**. **허용 규칙만** 가지며, 포트·IP 범위(IPv4/IPv6)로 인바운드/아웃바운드 트래픽을 제어한다.
- 소스로 IP 범위(`0.0.0.0/0`은 전체)뿐 아니라 **다른 보안 그룹을 참조**할 수 있다.
- 기본값: **인바운드 전부 차단, 아웃바운드 전부 허용**.
- 보안 그룹과 인스턴스는 다대다 — 한 보안 그룹을 여러 인스턴스에, 한 인스턴스에 여러 보안 그룹을 붙일 수 있다.
- 리전·VPC 단위로 존재한다. 리전을 바꾸면 새로 만들어야 한다.
- 인스턴스 밖에서 동작하므로, 차단된 트래픽은 인스턴스가 알 수조차 없다.
- **SSH 접속용 보안 그룹은 따로** 관리하는 것이 좋다.

| 증상 | 원인 |
|---|---|
| **타임아웃** | 거의 항상 **보안 그룹** 문제 |
| **연결 거부(connection refused)** | 트래픽은 통과함 → 애플리케이션이 안 떠 있거나 애플리케이션 오류 |

| 포트 | 용도 |
|---|---|
| 22 | SSH (리눅스 인스턴스 접속), SFTP |
| 21 | FTP |
| 80 / 443 | HTTP / HTTPS |
| 3389 | RDP (윈도우 인스턴스 접속) |

### IAM 역할

- Amazon Linux에는 AWS CLI가 기본 포함되어 있지만, 자격 증명이 없으면 `aws iam list-users` 같은 명령이 실패한다.
- 인스턴스 안에서 `aws configure`로 **액세스 키를 직접 넣는 것은 보안상 절대 권장하지 않는다.**
- 대신 인스턴스에 **IAM 역할**을 연결한다 (작업 → 보안 → IAM 역할 수정). 그러면 별도 키 없이 권한만큼 CLI/SDK를 쓸 수 있다.

### 퍼블릭 IP, 프라이빗 IP, 탄력적 IP

| | 식별 범위 | 특징 |
|---|---|---|
| **퍼블릭 IP** | 인터넷 전체 | 전 세계에서 유일. 인스턴스를 중지 후 시작하면 **바뀔 수 있음** |
| **프라이빗 IP** | 사설 네트워크 안 | 그 네트워크 안에서만 유일. 지정된 대역만 사용. 인터넷은 NAT/인터넷 게이트웨이를 통해 |
| **탄력적 IP** | 인터넷 전체 | 고정 퍼블릭 IPv4. 해제하기 전까지 계속 보유. 계정당 기본 5개 |

- EC2끼리는 AWS 내부의 프라이빗 IP로 통신하고, 외부(내 PC)에서 SSH로 붙을 때는 퍼블릭 IP를 쓴다.
- 탄력적 IP는 **할당만 하고 연결하지 않으면 요금이 나오므로**, 안 쓰면 연결 해제 후 릴리스한다.
- **탄력적 IP는 가급적 쓰지 않는다.** 대신 퍼블릭 IP에 DNS 이름(Route 53)을 붙이거나, **로드 밸런서를 앞에 두고 퍼블릭 IP를 아예 쓰지 않는 것**이 가장 권장된다.

### 배치 그룹

| 전략 | 배치 | 장점 | 단점 | 예 |
|---|---|---|---|---|
| **클러스터** | 모두 같은 AZ | 지연 짧고 처리량 높음 (향상된 네트워킹) | AZ 장애 시 전부 중단 | 빅데이터, HPC |
| **분산** | 서로 다른 하드웨어, 여러 AZ 가능 | 동시 장애 위험 최소 | AZ당 최대 7개 인스턴스 | 중요한 소수 인스턴스 |
| **분할** | 여러 AZ의 파티션(랙)에 분산 | 랙 장애로부터 안전, 파티션당 인스턴스 수 제한 없음 | AZ당 최대 7개 파티션 | HDFS, Kafka |

### ENI (Elastic Network Interface)

VPC 안의 가상 네트워크 카드. 인스턴스가 네트워크에 접근하게 한다.

## EBS와 스토리지

### EBS

- 인스턴스에 연결하는 **네트워크 드라이브**(네트워크 USB 같은 느낌). 네트워크를 거치므로 약간의 지연이 있을 수 있다.
- 인스턴스가 종료되어도 데이터가 남고, 분리해서 다른 인스턴스에 다시 연결할 수 있다.
- **특정 AZ에 고정**된다. 다른 AZ로 옮기려면 스냅샷을 이용한다. 볼륨을 만들 때 인스턴스와 같은 AZ를 골라야 한다.
- 용량과 IOPS를 미리 정해서 프로비저닝한다.
- 기본적으로 한 볼륨은 한 인스턴스에만 연결된다 (한 인스턴스에 여러 볼륨은 가능). 예외는 아래 다중 연결.
- 인스턴스 생성 시 **"종료 시 삭제"** 옵션이 있다. 루트 볼륨은 기본으로 체크, 추가 볼륨은 기본 해제.

### 스냅샷

특정 시점의 EBS 백업. 다른 AZ나 리전으로 복사할 수 있다.

| 기능 | 설명 |
|---|---|
| 아카이브 티어 | 최대 75% 저렴. 대신 복원에 24~72시간 |
| 휴지통 | 삭제한 스냅샷·AMI를 보존 규칙 기간(1일~1년) 동안 복구 가능 |
| 빠른 스냅샷 복원(FSR) | 스냅샷을 미리 완전 초기화해 첫 사용 지연을 없앰. 큰 볼륨을 빨리 띄워야 할 때. 비쌈 |

### AMI (Amazon Machine Image)

- 인스턴스로부터 만든 커스텀 이미지. 소프트웨어·설정·모니터링 도구를 미리 넣어 두면 **부팅과 설정 시간이 줄어든다.**
- 리전 단위로 만들고 다른 리전으로 복사할 수 있다. 마켓플레이스의 남이 만든 AMI도 쓸 수 있다.
- 절차: 인스턴스 설정 → 데이터 무결성을 위해 **중지** → AMI 생성(이때 EBS 스냅샷도 생성됨) → AMI로 새 인스턴스 시작

### 인스턴스 스토어

- 물리 서버에 **직접 붙은** 하드웨어 드라이브. EBS보다 I/O 성능이 훨씬 높다.
- 인스턴스를 중지·종료하면 **데이터가 사라지는 임시 스토리지**. 장기 보관용이 아니다.
- 버퍼, 캐시, 스크래치 데이터, 임시 콘텐츠에 쓴다. 하드웨어 장애 위험이 있으니 필요하면 백업·복제한다.

### 볼륨 유형

크기, 처리량, IOPS로 특성이 정해진다. **부팅 볼륨은 gp2/gp3, io1/io2(SSD)만** 가능하다.

| 유형 | 매체 | 크기 | 성능 | 용도 |
|---|---|---|---|---|
| gp3 | SSD | 1GB~16TB | 기본 3,000 IOPS·125MB/s, 최대 16,000 IOPS·1,000MB/s. IOPS·처리량을 용량과 **독립적으로** 설정 | 부팅 볼륨, 가상 데스크톱, 개발·테스트 |
| gp2 | SSD | 1GB~16TB | IOPS가 용량에 연동 (GB당 3 IOPS, 최대 16,000) | 〃 (구세대) |
| io1 / io2 | SSD | 4GB~16TB | 프로비저닝 IOPS. 최대 32,000 (Nitro 인스턴스는 64,000). io2는 같은 가격에 내구성·GB당 IOPS가 더 높음 | 16,000 IOPS 이상 필요하거나 성능·일관성에 민감한 **DB** |
| io2 Block Express | SSD | 4GB~64TB | 밀리초 미만 지연, 최대 256,000 IOPS | 최고 성능 |
| st1 | HDD | 125GB~16TB | 처리량 최적화, 최대 500MB/s·500 IOPS | 빅데이터, DW, 로그 처리 |
| sc1 | HDD | 125GB~16TB | 콜드 HDD, 최저 비용, 최대 250MB/s·250 IOPS | 자주 접근하지 않는 데이터 |

### EBS 다중 연결

- 하나의 볼륨을 **같은 AZ**의 여러 인스턴스에 연결한다. 각 인스턴스가 읽기·쓰기 권한을 모두 가진다.
- **io1, io2만** 가능하고, 한 볼륨에 최대 16개 인스턴스.
- 가용성을 높인 클러스터형 리눅스 애플리케이션, 동시 쓰기를 관리해야 하는 애플리케이션에 쓴다.
- XFS·ext4가 아닌 **클러스터 인식 파일 시스템**을 써야 한다.

### EBS 암호화

- 볼륨 안의 저장 데이터, 인스턴스–볼륨 간 전송 데이터, 스냅샷, 스냅샷으로 만든 볼륨이 모두 암호화된다.
- 암호화·복호화는 EC2와 EBS가 백그라운드에서 투명하게 처리하고, 지연 영향은 거의 없다. KMS 키로 AES-256.
- **암호화되지 않은 볼륨을 암호화하는 방법**: 스냅샷 생성 → 스냅샷을 **복사하면서 암호화** 체크 → 암호화된 스냅샷으로 볼륨 생성 → 인스턴스에 연결

### EFS (Elastic File System)

- AWS 관리형 **NFS**. **여러 AZ의 여러 인스턴스에 동시에 마운트**할 수 있다.
- 가용성·확장성이 높지만 비싸다 (gp2 EBS의 약 3배). 용량을 미리 정하지 않고 **쓴 만큼** 과금되며 PB 규모까지 자동 확장된다.
- 콘텐츠 관리, 웹 서빙, 데이터 공유, WordPress 등에 쓴다.
- 접근 제어는 보안 그룹으로 한다. 리눅스 기반 AMI만 호환(POSIX 파일 시스템). KMS로 저장 데이터 암호화 가능.

| 설정 | 옵션 |
|---|---|
| 성능 모드 | **범용**(기본, 지연에 민감한 웹 서버·CMS) / **최대 I/O**(지연은 길지만 처리량·병렬성 높음, 빅데이터·미디어 처리) |
| 처리량 모드 | 버스팅 / 프로비저닝(스토리지 크기와 무관하게 처리량 지정) / 엘라스틱(워크로드에 따라 자동 조절, 예측이 어려울 때) |
| 스토리지 계층 | 표준(자주 접근) / EFS-IA(드물게 접근, 저렴하지만 읽을 때 비용). 수명 주기 정책으로 이동 |

| | EBS | EFS | 인스턴스 스토어 |
|---|---|---|---|
| 연결 | 인스턴스 1개 (io1/io2 다중 연결 예외) | 여러 AZ의 여러 인스턴스 | 해당 인스턴스만 |
| 범위 | 한 AZ | 리전 (여러 AZ) | 물리 서버 |
| 영속성 | 유지 | 유지 | 중지·종료 시 삭제 |
| 과금 | 프로비저닝한 용량 | 사용량 | 인스턴스 요금에 포함 |

## ELB와 Auto Scaling

### 로드 밸런서

- 트래픽을 여러 인스턴스에 분산하고, 애플리케이션에 **단일 접근 지점**(고정 DNS 이름)을 제공한다.
- **헬스 체크**로 비정상 인스턴스를 감지해 트래픽을 보내지 않는다 (지정한 포트·경로로 요청해서 200이면 정상).
- SSL 종료(HTTPS 처리), 쿠키 기반 고정 세션, 고가용성, 외부(퍼블릭)·내부(프라이빗) 트래픽 분리.
- ELB는 AWS가 업그레이드·유지보수·고가용성을 책임지는 **관리형** 로드 밸런서다. 직접 구축보다 싸고 편하며 EC2, ASG, ECS, ACM, CloudWatch, Route 53, WAF 등과 통합된다.
- 보안 그룹 구성: 사용자 → 로드 밸런서(HTTP/HTTPS 허용), 인스턴스는 **로드 밸런서 보안 그룹에서 온 트래픽만** 허용해 직접 접근을 막는다.

| 종류 | 계층 | 특징 | 대상 그룹 |
|---|---|---|---|
| CLB (2009) | L4/L7 | 구세대, 비권장 | |
| **ALB** (2016) | L7 (HTTP, HTTPS, WebSocket) | 경로·호스트·쿼리스트링·헤더 기반 라우팅, HTTP→HTTPS 리다이렉트, HTTP/2, 동적 포트 매핑 → MSA·컨테이너(ECS) 환경에 적합 | EC2(ASG), ECS 태스크, **Lambda**, 프라이빗 IP |
| **NLB** (2017) | L4 (TCP, UDP, TLS) | 초당 수백만 요청, 지연 약 100ms(ALB 약 400ms), **AZ별 고정 IP** (탄력적 IP 지정 가능) | EC2, 프라이빗 IP, ALB (고정 IP + HTTP 규칙이 필요할 때 NLB 뒤에 ALB) |
| GWLB (2020) | L3 (IP 패킷) | 방화벽·IDS/IPS 등 서드파티 네트워크 어플라이언스 앞단. **GENEVE 프로토콜, 6081 포트** | EC2, 프라이빗 IP |

- **ALB 뒤의 서버는 클라이언트 IP를 직접 보지 못한다.** 원래 IP는 `X-Forwarded-For`, 포트는 `X-Forwarded-Port`, 프로토콜은 `X-Forwarded-Proto` 헤더로 전달된다.
- ALB는 **리스너 규칙**(조건 + 작업 + 우선순위)으로 여러 대상 그룹에 라우팅한다. 헬스 체크는 대상 그룹 단위.
- GWLB 흐름: VPC 라우팅 테이블이 바뀌어 모든 트래픽이 GWLB로 → 어플라이언스 대상 그룹에서 분석 → 정상이면 GWLB를 거쳐 원래 목적지로, 이상이면 드롭.

### 부가 기능

- **고정 세션(Sticky Session)**: 같은 클라이언트를 같은 인스턴스로 보낸다 (CLB, ALB). 로그인 정보 같은 세션 데이터를 잃지 않기 위해 쓰지만 **부하 불균형**을 일으킬 수 있다. 쿠키가 만료되면 해제된다.

  | 쿠키 | 생성 주체 | 이름 |
  |---|---|---|
  | 애플리케이션 기반 — 커스텀 | 대상(애플리케이션) | 대상 그룹별 지정 (`AWSALB`, `AWSALBAPP` 등 예약어 불가) |
  | 애플리케이션 기반 — 애플리케이션 쿠키 | 로드 밸런서 | `AWSALBAPP` |
  | 기간 기반 | 로드 밸런서 | ALB `AWSALB`, CLB `AWSELB` |
- **교차 영역(Cross-Zone) 로드 밸런싱**: AZ마다 인스턴스 수가 달라도 전체 인스턴스에 균등하게 분산한다.
- **SSL/TLS**: 인증서는 ACM으로 관리한다. **SNI**는 클라이언트가 접속할 호스트 이름을 알려주는 확장 프로토콜로, 하나의 서버(로드 밸런서)에 여러 인증서를 올려 여러 사이트를 지원하게 한다. ALB, NLB, CloudFront에서 사용.
- **연결 드레이닝(등록 취소 지연)**: 인스턴스가 등록 해제되거나 비정상일 때, 진행 중인 요청(in-flight)을 마칠 시간을 준다. 그 동안 새 요청은 보내지 않는다.

### ASG (Auto Scaling Group)

- 인스턴스 생성·종료를 자동화하고 스케일 인/아웃한다. 로드 밸런서와 연동된다.

| 조정 정책 | 방식 |
|---|---|
| 동적 스케일링 | 목표 추적 (예: CPU 40% 유지), 단계·단순 조정 |
| 예약 스케일링 | 알려진 패턴에 맞춰 시간 기반으로 |
| 예측 스케일링 | 과거 부하를 분석해 미리 확장 |

## RDS

- AWS **관리형 DB** 서비스. 프로비저닝 자동화, OS 패치, 지속적 백업과 특정 시점 복원, 모니터링 대시보드를 제공한다.
- 읽기 전용 복제본, 다중 AZ, 수직·수평 확장, 스토리지 오토스케일링을 지원한다. 스토리지는 EBS 기반.
- 관리형이라 **RDS 인스턴스에 SSH 접속은 불가**하다.

### Aurora

- AWS의 클라우드 네이티브 DB. 가용성이 높다.
- 단일 볼륨이 아니라 여러 AZ에 걸친 수백 개의 볼륨에 데이터를 나눠 저장한다.

### RDS 프록시

- 애플리케이션의 DB 연결을 **프록시가 풀링**해서 RDS로 가는 연결 수를 줄인다 → DB 부담 감소, 연결 타임아웃 감소.
- 서버리스, 오토스케일링, 고가용성.
- 장애 조치 시 대기 인스턴스로 연결해 **장애 조치 시간을 최대 66% 단축**한다.
- IAM 인증을 강제할 수 있다.
- 퍼블릭 접근이 불가능하고 VPC 안에서만 접근할 수 있다.

### ElastiCache

Redis 또는 Memcached를 관리형으로 제공한다.

## Route 53

### 레코드 타입

| 타입 | 매핑 |
|---|---|
| A | 호스트 이름 → IPv4 |
| AAAA | 호스트 이름 → IPv6 |
| CNAME | 호스트 이름 → 다른 호스트 이름 (그 이름은 결국 A/AAAA로 해석) |
| NS | 호스팅 존의 네임 서버 (DNS 쿼리에 응답하는 서버의 이름·IP) |

### 호스팅 존

- 레코드의 컨테이너. 도메인과 서브도메인으로 가는 트래픽을 어떻게 라우팅할지 정의한다.
- 퍼블릭 호스팅 존 / 프라이빗 호스팅 존(VPC 내부용).

### TTL (Time To Live)

클라이언트가 DNS 결과를 캐시하는 시간.

| TTL | DNS 요청 | 비용 | 레코드 변경 반영 |
|---|---|---|---|
| 길게 | 적음 | 적음 | 느림 |
| 짧게 | 많음 | 많음 | 빠름 |
